# AI 코어 프로젝트 2회차 회고록

> 진행 과정에서 확인된 사실과 결정 사항을 날짜순으로 기록한다. 당시 관찰과 계획은 뒤에서 실제 구현·검증 결과로 갱신하며, 실행하지 않은 결과를 성공으로 적지 않는다.

- 앱 이름: AqSolDB 수용해도 분석
- 도메인 후보: AqSolDB 기반 화합물 수용해도 분석
- 작성일: 2026-10-21
- 현재 단계: 출처 검증과 데이터 분석을 바탕으로 검색 UI를 정리하고 실행 점검 중
- 구현 상태: 로컬 근거 검색·출처별 예측 분석·수치 조건 검색을 구현; 벡터 검색과 답변 생성은 동의 기반으로 분리

## 1. 지금까지 한 일

1. 화학 데이터 사이언스 주제로 AqSolDB를 선택했다.
2. `train.csv`와 `test.csv`를 프로젝트 폴더에 준비했다.
3. 두 파일을 확인해 train 7,488행, test 2,494행을 확인했다. 실제 수용해도 열은 기획 초안의 `Solubility`가 아니라 `Y`였다.
4. 과제 요구사항을 다시 읽고 RAG 파이프라인과 근거 표시는 선택 기능이 아니라 필수임을 확인했다.
5. CSV 전체에서 일정 간격으로 300개 항목을 표본 추출해 InChIKey로 PubChem CID를 대조했다.

## 2. 확인된 결과

- 300개 표본 중 285개가 PubChem CID에 연결됐다.
- 179개에서 PubChem Record Description 설명 텍스트를 찾았다.
- boilerplate, 안전·위험 안내, 40자 미만 문장을 제외한 설명 후보는 118개였다.
- 표본 300개 중 PubChem 설명 항목에 원출처 인용까지 표시된 것은 41개였다.
- 설명 후보 100개 파일에는 PubChem URL을 모두 남겼다. 그중 26개는 PubChem에 원출처 인용이 있고, 나머지는 PubChem 기록까지만 확인됐다.
- 따라서 이 후보 파일은 출처 확인을 시작하기 위한 자료이지, 100개 모두의 원출처·이용 조건이 검증 완료된 최종 목록은 아니다.

추가 확인: Dataverse 공식 API 메타데이터에서 canonical v1 라이선스 CC0 1.0과 원본 파일 `curated-solubility-dataset.tab`을 확인했다. 또한 논문 Table 1의 A-I 원자료 출처 표를 행 ID 접두어와 연결해 LogS 값의 원자료를 추적할 수 있게 했다. 이 데이터 출처 추적과 PubChem 설명 annotation 출처 추적은 별개로 관리한다.

## 3. 잘된 점

- 항목 이름 문자열 대신 InChIKey를 사용해 구조 식별 기준으로 PubChem 기록을 대조했다.
- 데이터셋의 실제 CSV 열 이름과 행 수를 확인해 기획 초안을 바로잡았다.
- 항목 URL, PubChem CID, InChIKey, 원출처 인용 여부를 표에 남겨 나중에 출처를 다시 확인할 수 있게 했다.
- 데이터 분석과 RAG를 구분했다. 회귀 모델은 도메인 특화 기능 후보이고, RAG와 근거 표시는 필수 구현으로 정리했다.

## 4. 어려웠던 점과 배운 점

- AqSolDB에 화합물 정보가 있다고 해서, 각 화합물에 바로 쓸 수 있는 설명 문서와 원출처 인용까지 모두 있는 것은 아니었다.
- PubChem CID가 있다는 사실과 설명 문장·원출처·재사용 조건까지 확인했다는 사실은 서로 다르다.
- PubChem 응답은 항목마다 제공하는 설명과 주석이 달라, 일부 레코드는 별도 원출처 인용이 없었다.
- PubChem 요청을 반복할 때는 공개 API의 요청량 제한을 지켜야 한다.
- 결론: 주제는 계속 검토할 수 있지만, 출처 조건을 완전히 통과했다고 판단하기 전에는 최종 확정으로 표시하지 않는다.

## 5. 현재 의사결정

- AqSolDB 방향을 계속 진행한다.
- `pubchem_text_candidates_100.csv`는 후보 목록으로만 사용한다.
- AqSolDB 실험 데이터는 Dataverse v1 CC0 1.0 조건을 기록하고 논문 및 DOI를 인용한다. 원자료의 A-I 접두어도 보존한다.
- 원출처와 이용 조건이 확인된 PubChem 설명 문서를 우선 사용한다. 확인되지 않은 후보는 원출처를 보완하거나 다른 공개 문서로 대체하고, 확인이 안 되면 제외한다.
- 외부 문서의 출처·이용 조건을 확인한 뒤 요구사항 정의서와 RAG 파이프라인 설계문서를 정리한다. 100개 이상은 화합물 메타데이터 항목 조건이며 문서 수 조건이 아니다.

## 6. 다음 작업

1. 후보 목록의 각 행에서 원출처 인용과 이용 조건을 확인한다.
2. 원출처가 불명확한 화합물은 공식 출처·공공 문서·원 논문으로 보완하거나 제외한다.
3. 100개 이상 화합물 메타데이터를 유지하고, 실제로 색인할 각 외부 문서의 URL·제공처·원출처·이용 조건을 기록한다.
4. 출처 조건이 충족되면 요구사항 정의서와 RAG 파이프라인 설계문서를 작성한다.
5. 필수 기능 F2001~F2012를 구현하고, 실행 증거와 셀프 체크리스트를 단계별로 남긴다.
6. 구현 중 선택한 심화 기능과 RAG 사용 전후 품질 비교 여부를 결정한다.

## 8. 데이터 기본 점검 메모 (2026-10-21)

- train/test의 결측치와 중복 ID·InChIKey를 확인했다. 양쪽 모두 결측 셀과 각 파일 내부 중복이 없고, 분할 간 ID/InChIKey도 겹치지 않았다.
- 분할 간 동일 SMILES 문자열은 27종 있었다. AqSolDB에는 염·무기물 등의 부분 구조처럼 SMILES만으로는 식별이 부족해 보이는 사례가 있어, 다음 단계에서 RDKit 구조 파싱과 중복 정책을 검토한다.
- train/test의 `Y` 평균과 표준편차는 비슷했다. train `Group`은 G1 비중이 높아 그룹별 성능 확인을 평가 계획에 넣는다.
- 매핑 파일의 라이선스 열 이름을 바로잡았다. CC0 1.0은 Harvard Dataverse에 배포된 AqSolDB v1 라이선스 표시이며, 연결된 upstream 원자료 각각의 라이선스를 뜻하지 않는다.
- 기초 통계와 모델링 전 주의사항은 `docs/06_기초_데이터_점검.md`에 기록했다.

## 9. RAG 설계 초안 작성 (2026-10-21)

- 화합물 메타데이터와 외부 설명 문서를 별도 컬렉션으로 다루는 설계 초안을 만들었다.
- 답변에 문서 근거와 원문 URL을 연결하고, 출처 또는 이용 조건이 미확정인 자료를 제출용 색인에서 보류하도록 정했다.
- 아직 임베딩 모델, 벡터 DB, 청크 설정은 선택하지 않았다. 과제 요구사항 및 실습 환경과 맞춘 뒤 결정한다.
- 문서는 요구사항 번호별 대조와 문서 출처 확정 전의 초안이며, 구현 완료를 뜻하지 않는다.

## 10. 첫 회귀 기준선 기록 (2026-10-21)

- `train.csv` 안에서 Group 비율을 대략 유지한 80:20 검증 분할로 descriptor 17개 Ridge 회귀를 돌렸다. Group과 ID/SMILES, 측정 보조값은 입력에서 제외했다.
- 한 번의 검증 분할에서 MAE 1.146, RMSE 1.508, R² 0.593을 얻었고, train 평균 예측보다 낮은 MAE/RMSE였다. 이 수치는 초기 기준선이며 최종 성능이 아니다.
- 제공된 `test.csv`는 이번 실험에 쓰지 않았다. 반복 검증/모델 선택 후 최종 평가에 남겨둔다.
- 실행 코드와 설정은 `src/baseline_solubility.py`, 결과와 한계는 `docs/07_초기_회귀_기준선.md`에 정리했다.
- 실행 초기에 import 누락과 줄바꿈 삽입 문제를 만났고, 실행 가능한 스크립트로 고친 다음 결과를 기록했다.

## 11. 셀프 체크리스트 대조 (2026-10-21)

- 체크리스트 27개 항목과 요구사항 F2001-F2016/NF2001-NF2007을 대조했다. 아직 앱 기능 및 실행 증거가 없으므로 구현 확인 항목은 미확인으로 기록했다.
- 앞서 만든 RAG 초안에서 빠졌던 필수 조건(선택 항목 자체 문서 우선 포함, 메타데이터 근거 상시 포함, 두 노드 LangGraph, 항목별 대화 분리, 자연어 조건 필터, 검색어 수집 캐시)을 반영하도록 요구사항 초안을 구체화했다.
- 출처 중요도를 고려해 F2016을 심화 기능 후보로 제안했지만, 아직 확정하지 않았다.
- 현재 체크 상태와 다음 순서는 `docs/04_체크리스트_현재상태.md`, 도메인 기능별 수용 기준은 `docs/01_요구사항정의서.md`에 기록했다.
- 문서 지시는 과제 산출물·기능의 기준으로만 적용했다. 실제 완료 판정은 구현 실행과 증빙이 확보된 뒤에 한다.

## 12. 체크리스트 구현 착수 (2026-10-21)

- `UI/README.md`와 실행가이드의 영화 프로젝트는 전체 구조 참고용이고, `라이브_강의자료/step7_skeleton.py`, `step8_wiki_api.py`는 오후 프로젝트에 이어 쓰는 시작 골격임을 확인했다. 프로젝트 코드는 영화 도메인을 AqSolDB에 맞춰 바꾸되, 라이브 실습 파일은 수정하지 않는다.
- 라이브 실습 의존성과 프로젝트 의존성을 한 개의 `requirements.txt`로 합쳤다. 실습 원본 파일은 `reference/live_practice/`에 보관한다.
- `src/compound_data.py`에서 train/test 9,982개 행을 불러오고, 각 레코드를 단일 텍스트와 Chroma scalar 메타데이터로 만드는 것을 실행 확인했다. 이 단계는 F2001 준비이며, 실제 Vector DB 색인은 아니다.
- `src/index_metadata.py`는 고정 ID로 기존 항목을 건너뛰는 메타데이터 색인 명령으로 준비했다. 첫 실행은 GMS 임베딩 API 호출을 발생시키므로 실행하지 않았다.
- 프로젝트 README와 `.gitignore`를 추가해 출처/설치 흐름을 기록하고 `.env`·인덱스 디렉터리를 제외했다. 실제 비밀값은 열거나 기록하지 않았다.
- 체크리스트 대조표의 F2001은 진행 중으로 바꿨고, 나머지 기능 검증은 미확인으로 유지했다.

## 13. 출처 확인 범위 수정 (2026-10-21)

- 요구사항서의 “항목 수”와 F2001의 100개 이상은 화합물 메타데이터 수다. 외부 문서 100건을 요구하는 항목은 체크리스트에서 확인하지 못했다.
- 이전 계획 중 외부 문서를 100건까지 확인하려던 부분은 과한 범위라 정정했다. 실제 색인할 문서의 출처·이용 조건 확인은 계속하되, 미확정 후보 전체를 끝없이 조사하지 않는다.
- 모델을 높여도 출처 인용·이용 조건 자체의 증거가 생기지는 않는다. 검색어 초안과 후보 분류에만 보조적으로 사용한다.

## 14. 제출 전 폴더 정리 (2026-10-21)

- 데이터셋과 코드, 문서, 출처 조사자료, 라이브 실습 복사본을 `data/`, `src/`, `docs/`, `research/provenance/`, `reference/live_practice/`로 구분했다.
- 도메인 기획 초안의 데이터 열, 사용자 흐름, 저장 설계, 분석 범위와 표본 점검 내용을 요구사항 정의서에 통합하고 중복 기획 초안을 정리했다.
- 실습 및 프로젝트 의존성을 프로젝트 설치용 `requirements.txt`로 합쳤고, 원래 라이브 실습 의존성 파일은 참고 폴더에 보관했다.
- `.env`와 `.venv`는 로컬 실행을 위해 보존했다. 제출 안내에는 `.env`, 가상환경, 인덱스 캐시, 실습 원본 및 조사 중간자료를 제외하도록 적었다.
- 코드 경로를 새 `data/` 폴더 구조에 맞췄다. 임베딩 API는 호출하지 않았다.

## 15. 로컬 메타데이터 조회와 출처 재점검 (2026-10-21)

- 임베딩/API 호출 없이 이름, AqSolDB ID, InChIKey, descriptor 값으로 로컬 메타데이터를 찾는 `src/search_metadata.py`를 추가했다. 결과에 실험 LogS, 데이터셋 DOI/CC0 표기, A-I 원자료 코드와 논문 참고문헌 번호를 표시한다. 이 기능은 벡터 검색 또는 RAG가 아니다.

## 16. 프로젝트 질문 확정 및 출처 그룹 평가 (2026-10-21)

- 출처별 편차가 관찰됐지만, 이 결과만으로 원자료 출처가 오차 차이를 일으켰다고 말할 수 없다. 데이터 분포/측정 조건/그룹 크기 등의 영향이 가능하며, test.csv는 사용하지 않았다.

## 24. 첫 시연 경로와 프로젝트 범위 재점검 (2026-10-21)

- 이번 UI/문서 정리에는 GMS 호출이 필요하지 않아 크레딧을 쓰지 않았다. GMS는 임베딩·근거 답변 검증 때 호출 단위를 정해 아껴 사용한다.

## 25. RAG 과제와 포트폴리오 초점 재정렬 (2026-10-21)

- 요구사항 PDF 9~15쪽을 확인했다. 필수 범위는 두 컬렉션, 프롬프트 1·2·3, 항목별 검색·대화, 인용된 근거만 표시, 도메인 특화 기능에 검색 근거 제공, 자연어 조건 탐색이다. 분류 성능이나 GNN은 요구사항이 아니다.
- 외부 문서 쪽은 위험도가 높다. 당시 승인·색인된 자료는 세 화합물 발췌이며 프롬프트로 검색어를 뽑고 후보를 수집·선별하는 자동 흐름은 아직 없었다. 100~300개 화합물마다 문서가 필요하다고 요구사항에 적혀 있는 것은 아니다. F2001의 100개 이상은 메타데이터 수량이며, 문서가 없거나 식별되지 않은 항목을 억지로 근거가 있는 것처럼 보이면 안 된다.
- 가장 측정 가능한 차별화로 F2015를 우선 선택했다. 필수 파이프라인 후 같은 5개 이상 질문으로 RAG 전후의 근거성·인용 정확도·정답 보류를 기록한다. MMR은 시간이 남을 때만 비교한다.

## 26. 후보 수집 단계와 화면 위계 정리 (2026-10-21)

- `src/discover_wikipedia_candidates.py`를 추가해 GMS 검색어 추출 → 위키미디어 API 검색 → GMS 후보 선별 → 후보 원문·URL·화합물 ID·InChIKey·검토 상태 저장 흐름을 구성했다. 선택 물질 자체의 문서 후보가 검색되면 LLM 선별과 무관하게 포함한다.
- E-1274(아스피린)에서 실행해 10개 후보를 받았고 4개가 선별 목록에 들어갔다. 저장된 후보는 전부 `index_eligible=false`이며, 검색어 추출과 후보 선별용 GMS 호출 두 번을 사용했다. GMS 크레딧 차감량은 제공 대시보드에서 별도 확인하지 않아 숫자로 단정하지 않는다.
- 이 실험은 검색어/후보 선별 기술이 동작하는지 확인한 것이지, 외부 문서 근거를 색인·답변에 연결한 결과가 아니다. 검색 후보 중 아스피린의 직접 페이지와 관련성이 낮은 약물/시험 페이지가 함께 나와 후보 선별 오류 가능성이 확인됐다. 사람이 읽고 승인하기 전에는 색인하지 않는 정책이 필요하다.
- 위키백과 문서는 출처 제공자 링크만으로 attribution과 페이지별 이용 조건 검토가 완료되지 않는다. 기여자 표시, 원출처 및 선택 발췌의 재사용 범위를 확인한 뒤 승인 자료로 옮긴다.
- 앱 첫 화면에서 예측 카드가 근거 질의보다 앞서 보이던 순서를 바꿨다. 선택 화합물의 구조와 AqSolDB 실험 기록을 간결하게 먼저 보여주고, 근거 기반 질문을 접히지 않게 전면에 배치했다. LogS 회귀와 descriptor 이웃은 보조 분석 expander로 이동했다.
- 외부 문헌 근거가 없을 때에도 생성 모델이 AqSolDB 메타데이터만으로 답변을 만들어 낼 수 있던 공백을 확인했다. 메타데이터 관련 질문만 예외로 두고, 나머지 질문은 근거가 없으면 모델 API를 호출하지 않고 보류하도록 바꿨다. A-4518 pKa 질의에서 외부 근거 0건, 인용 0건의 보류 결과를 확인했다.
- GMS 키 누락 시 내부 예외 종류만 보여주던 화면을 `.env` 설정 방법 안내로 보완했다. 이번 변경에서 빠른 예시를 새로 추가하지 않았다.
- 명세서의 F2011을 다시 확인해 LLM 선별이 필수라는 이전 메모를 바로잡았다. 실제 요구는 자연어 수치 조건을 구조화하고 AqSolDB train 메타데이터에서 수치 조건을 결정적으로 재검사하는 것이다. 지원하는 세 문법을 로컬 데이터에서 확인했으며, 모호한 정성 표현은 임의 해석 대신 오류로 안내한다.
- F2010 회귀 보조 기능 옆에 모델 기준선·source-group holdout 범위·데이터셋 DOI와 해당 화합물의 승인 문헌 링크를 추가했다. 다만 문헌은 모델 설명이나 인과 증거가 아니므로 그 한계를 화면에 명시했다.
- 앱과 후보 스크립트는 `py_compile`로 문법을 확인했다. 수정된 화면을 localhost 브라우저에서 검증하려 했으나 8502가 응답하지 않았고, 8503 서버도 인앱 브라우저에서 시간 초과됐다. 네트워크 주소로 열려던 시도는 보안 정책이 차단해 중단했다. 따라서 UI 체크리스트 상태는 미확인이다.
- 후보 수집 스크립트가 반복 실행 때마다 GMS 검색어/선별과 외부 검색을 다시 호출하는 점을 줄이기 위해 성공한 화합물·질문 단위 캐시를 추가했다. 캐시 적중은 임시 경로에서 검증했고, 기존 후보를 승인하거나 색인하는 동작과 분리했다.
- F2005 비교는 실제 색인으로 확인했다. 기본 1,000/200 설정에서는 3청크, 임시 컬렉션에 150/30을 적용하면 7청크(화합물별 2·2·3건)였다. 비교용 임시 인덱스는 정리하고 기본 인덱스는 유지했다.

## 27. Top-k 검증과 화면 캡처 상태 (2026-10-21)

- A-4518에 같은 용해도 질문을 주고 결과 수 1과 3을 비교했다. 각 항목에 승인된 외부 문서가 하나뿐이라 두 설정이 동일한 한 근거를 반환했다. 검색 설정 자체보다 승인 문헌 수가 비교를 막고 있음을 확인했다. 출처와 재사용 조건을 검토하지 않은 후보를 인덱싱하지 않고, 승인 근거를 보강한 뒤 다시 비교하기로 했다.
- 제출 체크리스트는 증빙 스크린샷을 요구한다. Codex 인앱 브라우저에서 loopback 앱에 재접속했으나 시간 초과가 반복됐고, 캡처 파일은 만들지 않았다. 사용자 PC 브라우저에서 앱을 열어 실제 기능 화면을 캡처해야 한다.



## 28. 근거 출처 확장과 Top-k 재검증 (2026-10-21)

- A-4518의 근거가 하나뿐이라 Top-k를 바꿔도 결과가 같았던 원인을 데이터 폭에서 찾았다. 같은 분자의 외부 보조 자료를 추가하기 위해 Wikipedia 2-Methylpyridine 고정 revision을 열어 InChIKey/CAS/CID, 수용해도 항목, 라이선스, 신뢰도 안내를 확인했다. 해당 자료가 infobox 정확성을 보장하지 않는다는 경고를 보존하고, NOAA/NTP 정량값과 같은 출처 수준으로 취급하지 않도록 scope note를 명시했다.
- CC BY-SA 4.0 attribution과 라이선스 링크를 기록해 검토자료 및 컬렉션에 추가했다. 앱의 근거 카드에도 라이선스 조건과 조건 원문 링크를 표시하도록 연결했다.
- 승인 발췌는 세 건에서 네 건으로 늘었고 외부 Chroma 컬렉션에 한 청크를 추가했다. 같은 A-4518 질의를 GMS 벡터 검색으로 Top-k 1과 3에서 실행해 각각 1건과 2건을 반환하는 것을 확인했다. 근거 목록도 Wikipedia 단독에서 Wikipedia+NOAA/NTP로 달라졌다.
- 체크리스트 F2006은 검색 계층 기준 통과로 바꿨다. 인앱 브라우저 정책이 loopback 앱을 열지 못해 UI의 slider 조작과 스크린샷은 계속 미확인이다.


## 29. 반복 후보 탐색 캐시와 초기 UI 점검 (2026-10-21)

- E-1274 같은 질문의 후보 검색을 실제로 다시 수행했다. 캐시가 없던 첫 실행에서 검색어 추출·후보 검색·LLM 선별을 완료했고, 두 번째 실행은 완료 캐시를 사용해 GMS/API 재호출 없이 끝났다. 수집 후보는 사람이 검토하기 전 색인하지 않는 기존 정책을 유지했다.
- Streamlit AppTest 초기 렌더링에서 예외 0건을 확인했다. 이는 앱 코드가 초기 화면을 구성한다는 점만 확인하며, 사용자가 보는 브라우저의 반응형 레이아웃·상호작용·증빙 스크린샷은 확인하지 못했다.
- 따라서 NF2002/F2004는 반복 호출 생략 동작 기준으로 통과 처리했다. 체크리스트 종합 브라우저 검증과 제출용 스크린샷은 여전히 남아 있다.


## 30. 실제 답변의 인용 대조와 카드 표시 (2026-10-21)

- 최신 A-4518 벡터 근거를 사용해 답변을 생성했다. 모델의 AqSolDB LogS 인용값이 데이터 행과 일치했고, NOAA/NTP 수치와 Wikipedia의 비정량 보조 표기를 각각 구분했다. 인용 ID가 실제 검색 결과의 메타데이터·문헌을 가리키는지도 대조했다.
- AppTest에서 A-4518 검색을 실행하고 인용 ID에 해당하는 문헌 카드 두 건, 제목과 원문 링크가 표시되는지 확인했다. 예외는 없었다. 따라서 F2008을 통과 처리했으며, 이 자동 UI 확인은 여전히 실제 화면 스크린샷을 대신하지 않는다.


## 31. 외부 API 호출 식별 정보 (2026-10-21)

- Wikimedia Foundation의 User-Agent와 API 이용 정책을 확인했다. 사용자 에이전트에 운영자를 실제로 연락할 수 있는 이메일·웹사이트·Wikimedia 계정이 필요하다. 임의로 연락처를 만들면 안 되므로 프로젝트 `.env.example`에 `WIKIMEDIA_CONTACT` 설정을 추가하고, 후보 스크립트가 값이 없을 때 Wikimedia 네트워크 요청을 실행하지 않도록 했다. 실제 연락처는 사용자가 직접 `.env`에 넣어야 한다.
- 외부 GET에는 최소 1초 간격, HTTP 429/5xx 제한 재시도, 지수형 backoff, Retry-After 준수를 추가했다. 현재 연락처가 없어 실제 429 재시도 경로를 호출하지 않았으므로 NF2006 전체 통과로 처리하지 않는다.


## 32. 외부 컬렉션 재색인 멱등성 (2026-10-21)

- 네 번째 검토 문서를 색인한 뒤 전체 외부 자료를 다시 색인 명령에 넣었다. 기존 4 / 추가 0 / 총 4가 유지됐고 저장소의 영속 청크 수도 4였다. 중복 청크가 만들어지지 않았다.
