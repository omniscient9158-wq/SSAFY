# 🎬 Movie Lab — 영화 큐레이터 RAG

영화 메타데이터와 위키백과 문서에서 **근거를 찾아** 영화 관련 질문에 답하고,
그 **출처를 함께 제시하는** 채팅형 영화 큐레이터입니다.

SSAFY AI 코어 프로젝트 2회차 실습용 프로젝트로, RAG 파이프라인을 **두 번** 구성해 봅니다.

- **RAG 1** — 영화 메타데이터 964편을 Vector DB에 적재
- **RAG 2** — 질문에서 뽑은 키워드로 위키백과 문서를 수집해 Vector DB에 적재

## 빠른 시작

> 로컬 테스트·서버 배포의 전체 절차와 문제 해결은 **[실행가이드.md](실행가이드.md)** 에 있습니다.

```bash
# 1. 설치 (Python 3.12)
pip install -r src/requirements.txt

# 2. 키 설정 — src/.env.example 을 src/.env 로 복사한 뒤 채운다
#    GMS_KEY=발급받은_키          (https://gms.ssafy.io/web/)
#    INDEX_DIR=C:\movielab_indexes (영문 경로. 한글 경로에는 색인이 써지지 않는다)

# 3. 영화 메타데이터 색인 (최초 1회, 1분 내외)
python src/index_movies.py

# 4. 위키 원문 색인 (최초 1회, 5~10분) — 배포 압축본의 resources/rag/wikipedia/ 가 있어야 한다
python src/repair_wiki_index.py --apply
python src/repair_wiki_index.py          # 검증: "유실 0쌍"이 나와야 한다
python src/collect_wikidata.py --reindex # 위키데이터 원문 → 색인 (F2016, 수 초)

# 5. 앱 실행 — 둘 중 하나만 띄운다 (같은 색인을 쓰므로 동시에 띄우지 않는다)
streamlit run src/app.py          # Streamlit 화면       → http://localhost:8501
python src/server.py              # HTML·CSS·JS 화면(F2013) → http://localhost:8000
```

`data/movies.json`이 저장소에 포함되어 있으므로 영화 목록은 다시 모을 필요가 없습니다.
**4번을 건너뛰면 위키 근거가 비어 사실 질문이 모두 "문서로 확인 불가"로 나옵니다.**
(`wiki_manifest.json`이 964편을 "수집 완료"로 기록하고 있어 질문 시점 수집도 일어나지 않습니다)
영화 목록을 직접 다시 모으려면 아래 "데이터 다시 수집하기"를 참고하세요.

## 사용법

1. 왼쪽 사이드바에서 질문할 영화를 고릅니다.
2. 채팅창에 질문을 입력합니다.
3. 시스템이 관련 위키 문서를 수집·색인한 뒤 답변합니다.
   배포본은 964편 전량의 문서를 미리 모아 두어 첫 질문도 4~13초에 끝납니다.
   코퍼스 없이 새로 수집하면 영화 1편당 1~2분이 걸립니다.
4. 답변 아래 **근거 문서** 목록에서 어떤 문서를 참고했는지, 원문 링크가 무엇인지 확인합니다.

질문 예시

- `이 영화 감독의 다른 작품은?`
- `영화 명량에서 이순신이 13척으로 왜군을 물리치는데, 실제 역사도 그런가?`
- `기생충의 반지하는 실제 한국 주거 형태인가?`

## 동작 원리

```
[사전 준비]  data/movies.json (964편)
                └→ 영화 1편 = 청크 1개 → Embedding → ChromaDB: movie_meta      (RAG 1)

[질문 시점]  질문 + 선택한 영화
                └→ (프롬프트 1) LLM이 위키 검색 키워드 추출
                   └→ Wikipedia API 검색 → 후보 수집
                      └→ (프롬프트 2) LLM이 쓸 문서를 고른다 + 본편 문서는 무조건 첫 자리
                         └→ 본문 수집 → 1000자 청킹 → Embedding → ChromaDB: movie_wiki  (RAG 2)
                └→ TMDB ID(P4947)로 위키데이터 항목 조회 → 사실 줄 단위 청킹 → ChromaDB: movie_wikidata  (F2016)

[답변]       LangGraph
                retrieve : 메타데이터 + 위키백과(MMR) + 위키데이터 → 병합 → 중복 제거 → [근거 N] 번호 부여
                generate : (프롬프트 3) 검색된 문서만 근거로 답변
```

### 두 종류의 문서 출처 (F2016)

| | 위키백과 | 위키데이터 |
| --- | --- | --- |
| 성격 | 서술형 문서 (배경·사건·해설) | 구조화된 사실 ("속성: 값") |
| 찾는 방법 | LLM 검색어 추출 → 후보 선별 (프롬프트 1·2) | TMDB ID(P4947)로 영화 항목 하나를 바로 조회 |
| 청킹 | 1,000자 · 200자 중복 | **줄 단위**, 중복 없음, 청크마다 영화 제목 머리줄 |
| 검색 | 질문과의 유사도 (MMR) | 영화당 1~3청크라 **검색 없이 전부** 근거에 넣음 |
| 컬렉션 | `movie_wiki` | `movie_wikidata` |
| 근거 표시 | `위키백과` | `위키데이터` |

청킹을 다르게 한 이유: 위키데이터는 "수상: 아카데미 시각효과상 (2015)"처럼 한 줄이 사실 하나라,
글자 수로 자르면 속성명과 값이 다른 청크로 갈라집니다. 검색하지 않고 전부 넣는 이유는
"수상", "흥행 수입"처럼 한 줄짜리 사실이 질문 문장과 유사도가 낮아 빠지기 때문입니다.
위키데이터는 개봉일·배역·수상·흥행 수입처럼 **위키백과 본문에 흩어져 있거나 빠진 정확한 값**을 보충합니다.

검색 결과를 그대로 받지 않고 **후보를 모은 뒤 LLM이 한 번 더 고르는** 2단 구조입니다.
문자열 매칭으로 관련성을 판정하던 방식은 번역어·별칭을 넘지 못해 정답을 버렸습니다.
(`NASA` → `미국 항공 우주국`, `하비 덴트` → `투페이스`)

단, **그 영화 자체를 다룬 문서(본편 문서)만은 LLM 판단에 맡기지 않습니다.** 모든 근거의
기준점이라 후보에 있으면 무조건 첫 자리를 주고, 길이 기준도 적용하지 않습니다(F2004). 그러지 않으면
시리즈물에서 본편 대신 시리즈 문서가 뽑히거나(`반지의 제왕: 왕의 귀환` →
`반지의 제왕 (영화 시리즈)`) 짧다는 이유로 잘려나갑니다.

### 다섯 개의 프롬프트

|            | 위치                    | 역할                                          |
| ---------- | ----------------------- | --------------------------------------------- |
| 프롬프트 1 | `src/collect_wiki.py` | 영화·질문에서 위키 검색 키워드를 뽑는다      |
| 프롬프트 2 | `src/collect_wiki.py` | 위키 검색 결과 중 색인할 문서를 고른다        |
| 프롬프트 3 | `src/rag_graph.py`    | 검색된 문서만으로 판정·답변·근거를 구성한다 |
| 프롬프트 4 | `src/recommend.py`    | 검색된 후보 영화 중 요청에 맞는 것을 고른다   |
| 프롬프트 5 | `src/review.py`       | 영화 한 편의 관람 가이드를 쓴다               |

1~3번은 요구사항정의서 2.4의 번호(검색어 추출 · 후보 문서 선별 · 답변 생성)와 같습니다.

## 설정

`src/.env`에서 조정합니다. 값이 없으면 괄호 안의 기본값을 씁니다.

| 항목                                 | 설명                                               |
| ------------------------------------ | -------------------------------------------------- |
| `GMS_KEY`                          | **필수.** SSAFY GMS API 키                   |
| `TMDB_KEY`                         | 영화 데이터를 다시 수집할 때만 필요                |
| `CHAT_MODEL`                       | 답변·추천·관람 가이드 모델 (`gpt-5.4-nano`)    |
| `KEYWORD_MODEL` / `SELECT_MODEL` | 키워드 추출·문서 선별 모델 (`gpt-5.4-nano`)     |
| `EMBEDDING_MODEL`                  | 임베딩 모델 (`text-embedding-3-small`, 1536차원) |
| `CHUNK_SIZE` / `CHUNK_OVERLAP`   | 위키 문서 청킹 (`1000` / `200`)                |
| `WIKIDATA_CHUNK_SIZE`              | 위키데이터 청크 크기 (`1000`, 줄 단위·중복 없음) |
| `TOP_K_MOVIE`                      | 영화를 고르지 않았을 때 메타데이터 검색 결과 수 (`3`) |
| `TOP_K_WIKI`                       | 위키 검색 결과 수 (`10`)                         |
| `INDEX_DIR`                        | 벡터 색인 위치 (`resources/indexes`). **Windows에서 프로젝트 경로에 한글이 있으면 영문 경로로 지정** (예: `C:\movielab_indexes`). chromadb가 비ASCII 경로에 벡터 파일을 쓰지 못한다 |
| `USE_MMR` / `FETCH_K`            | MMR 사용 여부 (`1`) / 후보 수 (`30`)           |
| `INCLUDE_SIMILAR_MOVIES`           | 다른 영화도 근거에 넣을지 (`0`)                  |

### 모델과 답변 품질

**답변 품질은 `CHAT_MODEL`의 성능에 따라 크게 달라질 수 있습니다.** 같은 문서를 근거로
주더라도 작은 모델은 판단을 보수적으로 내려, 사실 확인 질문에 "문서로 확인 불가"를 자주
답합니다. 문서에 답이 있어도 질문과 똑같은 문장이 없으면 판정하지 못하는 식입니다.

같은 프롬프트·같은 검색 결과로 사실 확인 질문 6개를 돌린 결과입니다. (2026-09-30, 1회 측정)

| `CHAT_MODEL`                  | "문서로 확인 불가" 판정 | 비고                                        |
| ----------------------------- | ----------------------- | ------------------------------------------- |
| `gpt-5.4-nano`                | 5 / 6                   | 근거를 인용하고도 판정을 내리지 못함        |
| `gpt-5.4-mini` (effort=low)   | 2 / 6                   |                                             |
| `gpt-5.4`                     | 1 / 6                   | 근거로부터 판단하고, 세부 각색을 구분해 설명 |

- `gpt-5.4` 계열은 추론(reasoning)이 기본으로 꺼져 있습니다. 추론을 켠다고 판정이 적극적으로 바뀌지는 않았습니다.
- 모델이 커질수록 응답 시간과 비용이 늘어납니다. `CHAT_MODEL`은 질의응답뿐 아니라 추천·관람 가이드에도 쓰입니다.
- 같은 모델이라도 실행할 때마다 판정이 달라질 수 있습니다. 모델을 바꾸면 정답을 아는 질문 몇 개로 먼저 확인하세요.
- 위 표는 답변 프롬프트가 영화 장면·줄거리에 일반 지식 보충을 허용하던 때에 잰 값입니다. 지금은 검색된 문서만
  쓰도록 바뀌어(요구사항 F2007) 수치가 달라질 수 있습니다.
- "문서로 확인 불가"가 많다면 모델보다 **색인 상태를 먼저 확인**하세요. 색인이 비어 있거나 손상되어도 오류 없이 같은 증상이 나타납니다. (`python src/debug_search.py <movie_id> "질문"`)

수집 관련 상수는 `src/config.py`에 있습니다. `.env` 열의 값은 `src/.env`로도 바꿀 수 있습니다.

| 상수                   | 기본값 | `.env` | 설명                                                         |
| ---------------------- | ------ | ------ | ------------------------------------------------------------ |
| `KEYWORD_COUNT`      | 9      | ✅     | LLM이 뽑을 검색 키워드 수                                    |
| `SEARCH_LIMIT`       | 8      | ✅     | 키워드당 확인할 검색 결과 수                                 |
| `MAX_PAGES`          | 12     |        | 영화당 색인할 문서 총량 상한                                 |
| `MIN_TEXT_LENGTH`    | 350    | ✅     | 이보다 짧은 문서는 색인하지 않는다                           |
| `CORE_MIN_LENGTH`    | 300    |        | **감독 문서 기준.** 본편 문서는 길이와 관계없이 받는다 (F2004) |
| `SECOND_ROUND`       | 1      | ✅     | 1차 수집이 상한을 못 채우면 다른 각도의 키워드로 한 번 더 수집 |
| `MORE_KEYWORD_COUNT` | 6      | ✅     | 2차 라운드에서 추가로 뽑을 키워드 수                         |

한국어 위키백과는 영어판보다 문서가 훨씬 짧아, `MIN_TEXT_LENGTH`를 800자로 두면 관련성이 높은
문서도 무더기로 탈락합니다. (`듄 (소설)` 783자, `범죄심리학` 434자, `드니 빌뇌브` 274자)
그래서 350자로 낮췄고, 감독 문서는 `CORE_MIN_LENGTH`(300자)를 따로 적용합니다. 본편 문서는 길이와 관계없이 받습니다.
800자 기준에서는 `헝거 게임: 캣칭 파이어`(671자), `300 (영화)`(755자), `정이 (영화)`(436자) 같은
본편 문서가 먼저 잘려나갔습니다.

## 배포본 사전 구축 (운영자용)

이 저장소는 **완성본(시연용)**입니다. 교육생은 요구사항명세서를 보고 각자 구현하므로
이 코드를 그대로 쓰지 않습니다. 사전 구축은 두 가지 목적으로 합니다.

1. **시연용 코퍼스** — 완성본을 보여줄 때 첫 질문부터 즉시 답이 나오도록.
2. **폴백 데이터셋** — 교육장에서 위키 호출 한도에 걸릴 경우, 수집해 둔 원문
   (`resources/rag/wikipedia/*.json`)을 배포해 교육생의 수집 단계를 대신하도록.

벡터 색인은 폴백이 될 수 없습니다. 교육생마다 청크 크기·메타데이터 스키마·임베딩
모델이 다르므로 재사용이 불가능합니다. 배포할 수 있는 건 **원문 JSON뿐**입니다.

```bash
python src/select_movies.py                  # 대상 선정 (해외 200 + 한국 100)
python src/prebuild_wiki.py --pages 5        # 수집·색인 (중단해도 이어서 진행)
python src/prebuild_wiki.py --fill-own       # 본편 문서가 빠진 영화만 보강 (LLM 미사용)
python src/repair_wiki_index.py --apply      # 색인 정합성 확인·복구
python src/repair_wiki_index.py --compact --apply   # 삭제 후 남은 빈 슬롯 정리
```

현재 배포본은 **964편 전량 · 문서 3,711건 · 청크 36,199개**(수집 원문 JSON 3,763개 · 57MB)이고,
색인 크기는 `movie_wiki` 635MB + `movie_meta` 18MB입니다.

색인 용량은 임베딩 차원이 정합니다. 1,000자 청크 하나가 1536차원 float32 = 6KB로,
원문 텍스트(약 3KB)보다 벡터가 큽니다. 여기에 Chroma가 본문 사본과 전문검색 인덱스를
얹어 원문 23MB가 색인 230MB가 됩니다.

`delete`는 HNSW 파일을 줄이지 않고 슬롯을 비워 둔 채로 둡니다. 청크를 대량으로 지우거나
ID를 바꾼 뒤에는 `--compact`로 털어내야 합니다. (실제로 복구 작업 뒤 81MB가 남아 있었습니다)

| 명령                        | 용도                                             |
| --------------------------- | ------------------------------------------------ |
| `--reset`                 | 이전 수집분을 모두 비우고 처음부터               |
| `--refill N`              | 문서가 N건 미만인 영화만 지우고 다시 수집        |
| `--movies <id,id>`        | 지정한 영화만 지우고 다시 수집                   |
| `--fill-own`              | 기존 문서를 두고 본편 문서만 추가 (손실 없음)    |
| `--add-own "<id>=<제목>"` | 본편 문서를 직접 지정 (위키 제목이 크게 다를 때) |
| `--diagnose`              | 키워드가 어디서 탈락했는지 단계별 기록           |

키워드 추출은 비결정적이라 **재수집은 돌릴 때마다 결과가 달라집니다.** 이미 좋은 문서를
갖고 있다면 `--fill-own`처럼 더하기만 하는 명령을 쓰고, 재수집은 정말 필요할 때만 씁니다.
`마녀 2`처럼 한국어 위키 제목이 영화 제목과 전혀 다른 몇 편은 `--add-own`으로 못박아 둡니다.

## 웹 API (F2013)

`python src/server.py`가 JSON API와 화면(`src/web/`)을 함께 제공합니다. 화면은 이 API만 호출하고,
API 키는 서버 환경변수에만 있습니다. 자동 생성된 API 문서는 `/api/docs`에서 볼 수 있습니다.

| 메서드 | 경로 | 요청 본문 | 응답 |
| --- | --- | --- | --- |
| GET  | `/api/status` | — | `{indexes: {movie_meta, wikipedia, wikidata}, api_key, chat_model, movies}` |
| GET  | `/api/movies` | — | `[{movie_id, label}]` |
| GET  | `/api/movies/{id}` | — | 영화 정보 + `wiki_titles`, `wikidata`, `similar` |
| POST | `/api/movies/{id}/collect` | `{question}` | `{added_titles, titles, wikidata: {status, qid, chunks}}` |
| POST | `/api/ask` | `{movie_id, question}` | `{answer, sources: [{index, title, source_type, source_label, url}], cited}` |
| POST | `/api/movies/{id}/review` | — | `{review, sources, cited}` |
| POST | `/api/recommend` | `{query}` | `{query, results: [{movie_id, label, genres, director, reason}]}` |

- `sources`에는 답변 본문이 실제로 인용한(`[근거 N]`) 근거만 들어갑니다. 인용이 하나도 없으면 `sources`는 빈 목록,
  `cited`는 `false`이고 화면은 "답변에 인용된 근거가 없습니다"를 안내합니다. (F2008)
- 오류는 `{detail: "안내 문구"}` 한 가지 형식입니다. 입력 오류 422, 없는 영화 404, 처리 실패 500.
  오류 추적 정보는 화면에 보내지 않고 서버 로그에만 남깁니다. (NF2004)
- 화면은 수집(`collect`)과 답변(`ask`)을 나눠 불러 "문서 확인 중 → 답변 생성 중" 진행 상태를 보여줍니다.
- chromadb 클라이언트를 여러 스레드가 동시에 열면 오류가 나므로, 색인·LLM을 쓰는 요청은 서버에서 한 번에 하나씩 처리합니다.
  동시에 여러 요청이 오면 뒤 요청은 앞 요청이 끝날 때까지 기다립니다.
- `/?movie=<영화 ID>`로 들어오면 그 영화의 대화가 바로 열립니다.

## 데이터 출처와 이용 조건

| 데이터 | 출처 | 이용 조건 |
| --- | --- | --- |
| 영화 메타데이터 | TMDB API | TMDB API 이용약관 — 출처(TMDB) 표기 |
| 위키백과 문서 | 한국어 위키백과 API | CC BY-SA 4.0 — 출처(원문 링크) 표기, 동일 조건 변경 허락 |
| 위키데이터 사실 | 위키데이터 API | CC0 1.0 (퍼블릭 도메인) |

근거 목록의 원문 링크가 출처 표기 역할을 합니다. 위키미디어 API는 `WIKI_CONTACT`(연락처가 들어간 User-Agent)를
설정하면 분당 200회, 없으면 분당 10회로 제한됩니다. 요청 제한(429)과 일시적인 네트워크·서버 오류는 대기 후 재시도합니다. (NF2006)
끝내 실패한 검색어는 수집 이력에 남기지 않아 다음 질문에서 다시 수집합니다. (F2004·NF2002)

| **추가 기능** | ✅ 영화 추천(프롬프트 4) · 관람 가이드 생성(프롬프트 5) · 비슷한 작품       |
| **수집 품질** | ✅ LLM 문서 선별(프롬프트 2), 본편 문서 우선 색인, 청크 ID에 영화 식별자 포함 |
| **심화 F2013** | ✅ HTML·CSS·JavaScript 화면(`src/web/`) + FastAPI 서버(`src/server.py`) 분리 |
| **심화 F2014** | ✅ MMR 검색으로 근거 다양성 확보 (top-k 10 / 후보 30)                        |
| **심화 F2015** | ✅ RAG 사용 전후 답변 비교 (`src/compare_rag.py` → `outputs/rag_compare/`) |
| **심화 F2016** | ✅ 위키백과 + 위키데이터 결합, 근거에 출처 종류 표시                          |
| **그 외**     | ➖ 질의 재작성 · 검색 결과 재순위 · 근거 검증 루프 — 범위 제외             |

LangGraph 노드는 `retrieve`·`generate` 두 개입니다. 다양성 확보는 별도 재순위 노드 대신
검색 단계의 MMR로 해결했고, 파이프라인은 두 노드로 유지했습니다.

응답 시간은 사전 구축 코퍼스 기준 **4.8~13.4초**(질문 4건 실측)입니다.
